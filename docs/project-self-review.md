# 项目自评

## 1. 总体结论

当前项目已经完成训练营课题要求的主要闭环：

```text
用户登录
  -> AI 生成图文内容
  -> 编辑器人工确认
  -> 草稿保存与离线同步
  -> 发布前审核
  -> 合规改写
  -> 质量评分
  -> 榜单分发
  -> 内容详情与排序解释
```

我对当前作品的判断是：它已经是一个可运行、可演示、证据链相对完整的 MVP，而不是单纯页面原型或单点 AI demo。它的主要价值在于链路完整、边界清楚、评估材料可复用；主要不足在于仍有明显的演示系统属性，距离生产系统还有认证、存储、治理、部署稳定性等差距。

## 3. 评分维度对照

### 3.1 AI 工具深度应用与人机协同

当前 AI 能力覆盖生成、审核、改写和评分四个环节。相比只做“输入 prompt 得到文章”，项目把 AI 放到了创作者真实链路中的多个决策点：

- 生成阶段：产出标题、摘要、正文、封面建议、配图建议和标签。
- 编辑阶段：支持段落级局部重写，而不是整篇覆盖。
- 审核阶段：对风险内容拦截，并展示命中片段和处置建议。
- 改写阶段：在保留原意的基础上替换高风险表达。
- 分发阶段：质量评分进入榜单排序。

人机协同的核心设计是：AI 提供草稿、建议和结构化判断，人保留编辑、确认和再次发布的控制权。

不足：当前真实模型调用耗时较长，生成约 26s，评分约 24s；因此演示默认使用 Mock Provider。生产化时需要异步任务、流式反馈、超时降级和任务队列。

### 3.2 端到端体验与产品氛围

主链路已经通过 E2E 覆盖：

```text
登录 -> AI 生成 -> 草稿保存 -> 发布审核 -> 榜单 -> 详情
```

关键分支也已覆盖：

- 离线草稿恢复。
- 发布后编辑。
- 审核失败与合规改写。
- 内容下线治理。
- 不同榜单权重。

不足：当前 UI 可以支撑演示，但还不是成熟产品级的精细体验。比如素材上传仍是演示素材，榜单反馈指标是模拟值，运营后台配置能力较弱。

### 3.3 架构设计与性能优化

工程采用 Next.js App Router + Route Handlers + Prisma Repository 的单仓库方案。业务逻辑没有直接散落在页面里，AI、审核、排序、数据访问都有明确边界。

性能证据：

```text
公网入口 /feed/hot LCP = 1488ms
目标阈值 = 2500ms
```

不足：当前公网地址是 Cloudflare quick tunnel，不是长期生产部署。后续如果换到稳定环境，需要重新测 LCP、冷启动、缓存和真实网络波动。

### 3.4 内容安全与质量闭环

当前已经建立：

- 安全规则库。
- 结构化审核输出。
- 高危拦截。
- 合规改写。
- 质量评分。
- 质量分进入榜单排序。
- 样例集和评估脚本。

当前评估结果：

```text
Audit cases: 33/33
Quality cases: 3/3
Eval schema failures: 0
```

需要谨慎说明：这只是当前样例集内的基线，不代表真实线上泛化准确率。课题中“高危识别准确率 90% 以上”是目标要求，当前项目已经搭建评估方法，但还需要更大规模人工标注样例和真实模型对比才能严肃证明。

## 4. 当前边界

### 4.1 Mock 认证边界

登录注册是 Mock 认证，适合训练营演示和链路验证，但不包含真实生产系统所需的密码加密、验证码、账号风控、权限分层和审计。

### 4.2 Mock Provider 边界

默认 AI Provider 是 Mock，原因是演示和 E2E 需要稳定、快速、可重复。真实模型 smoke test 已验证四类任务可通过 schema，但真实模型耗时较长，不适合作为现场演示主路径。

### 4.3 审核准确率边界

当前 33 条审核样例集内通过率为 100%，但样例数量和覆盖面不足以证明真实线上泛化。合理表述应是：

```text
当前系统具备审核评估能力，样例集基线通过；未来需要扩展人工标注样例和真实模型对比，才能证明高危识别准确率。
```

### 4.4 数据与部署边界

当前数据存储是 SQLite，适合本地和演示。公网地址是 Cloudflare quick tunnel，适合提交前体验和演示预览。正式长期服务需要迁移到稳定部署环境，并考虑 PostgreSQL、对象存储、日志监控和备份。

### 4.5 内容治理边界

当前只实现了下线能力。真实平台还需要：

- 人工复核队列。
- 内容恢复。
- 版本回滚。
- 操作人和操作原因记录。
- 用户申诉或复审流程。

## 5. 做得比较好的地方

1. **主链路优先**  
   项目没有在一开始分散到很多孤立功能，而是先跑通创作、审核、发布、分发和详情。

2. **AI 输出有边界**  
   所有 AI 输出都通过 Zod schema，不让自由文本直接进入业务层。

3. **证据链完整**  
   功能不是只靠口头说明，配套有 E2E、evals、AI 调用日志、真实模型 smoke test 和线上 LCP。

4. **文档随工程演进**  
   需求、架构、审核、评估、worklog 和提交清单都在仓库中留存，便于复盘。

5. **边界没有包装成完成品**  
   文档明确说明 Mock、SQLite、quick tunnel、样例集准确率等边界。

## 6. 不足与改进方向

| 不足 | 影响 | 后续改进 |
| --- | --- | --- |
| 认证是 Mock | 无法用于真实用户 | 接入真实账号体系、密码加密、验证码和权限 |
| SQLite 本地数据库 | 不适合多人和长期运行 | 迁移 PostgreSQL，补迁移和备份 |
| 素材管理较简化 | 不支持真实上传和对象存储 | 接入对象存储、文件扫描、素材审核 |
| 审核样例数量有限 | 无法证明真实 90% 准确率 | 扩展 50+、100+ 人工标注样例，记录误杀和漏判 |
| 真实模型耗时长 | 不适合现场同步演示 | 改为异步任务、进度反馈、缓存和重试 |
| 内容治理只实现下线 | 治理闭环不完整 | 增加人工复核、恢复、撤回、回滚 |
| 部署是 quick tunnel | 无长期 SLA | 换稳定部署平台并复测 |
| 未接开放 API | 缺少热点真实数据源 | 后续接入头条 / 抖音开放 API 或模拟热点源 |

## 7. 长期建设路线

### 阶段一：提交前稳定化

- 在提交模板中回填演示视频飞书链接。
- 创建飞书提交模板副本。
- 清理 Git 状态并推送 GitHub `main/master`。
- 生成不含敏感信息的代码压缩包。

### 阶段二：生产化基础

- 替换 Mock 认证。
- SQLite 迁移 PostgreSQL。
- 素材接入对象存储。
- 将 quick tunnel 替换为稳定部署地址。
- 增加错误日志和调用监控。

### 阶段三：AI 效果评估深化

- 扩展审核样例集。
- 建立人工标注字段。
- 对比 Mock、火山方舟和其他兼容模型。
- 记录 Prompt 版本、schema 失败率、误杀率、漏判率和平均耗时。

### 阶段四：内容分发生态增强

- 接入真实热点数据或开放 API。
- 引入用户反馈闭环。
- 将榜单权重迁移到运营配置。
- 建立内容生命周期治理后台。

## 8. 自评结论

如果按训练营课题评分口径看，当前项目的核心价值是：

- 完整链路已经跑通。
- AI 能力不止生成，覆盖审核、改写、评分。
- 架构边界清楚，后续可替换。
- 评估和性能证据比较扎实。

当前项目仍是 MVP，不是生产平台。最应该在答辩中坦诚说明的边界是：Mock 认证、SQLite、quick tunnel、素材上传简化、审核样例规模有限。只要这些边界说清楚，项目的工程思路是站得住的。
