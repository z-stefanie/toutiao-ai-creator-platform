## 官方文档复核结论

### 项目课题 PDF 的硬要求

PDF 明确要求项目不是单点 AI API 接入，而是完整的：

```text
创作
  -> 审核
  -> 分发
  -> 反馈
  -> 优化
```

核心模块：

- AIGC 内容创作全链路。
- AI 内容安全与质量防火墙。
- 热点 / 爆文 / 推荐榜单与性能优化。

关键硬指标：

- 高危内容识别准确率目标不低于 90%。
- 榜单首屏 LCP 不多于 2.5 秒。
- 系统需要部署到线上环境，提供公开 URL 或二维码。
- 技术方案与架构设计文档需要清晰阐述架构、选型和核心模块。
- 代码需要托管到 GitHub，并最终提交到 `main` 或 `master` 分支。

评分权重：

- AI 工具深度应用与人机协同：30%。
- 端到端完整体验与产品氛围：30%。
- 架构设计与性能优化：20%。
- 内容安全与质量闭环：10%。
- 工程化与交付规范：10%。

### 提交模板的硬要求

提交模板要求填写：

- 基本信息：项目名称、作者、技术栈。
- 体验地址：在线访问地址、测试账号 / 密码、3-5 分钟演示视频。
- 项目介绍文档：简介、核心功能、亮点、截图 / GIF、完成度清单。
- 项目技术文档：架构、选型、核心模块、AI 接入、数据库、性能、工程化。
- 审核规则与质量评估体系。
- 效果评估与优化报告。
- 代码压缩包：完整项目代码、README、启动说明、测试说明。
- 项目自评：不足与长期建设思路。

## 对 Step 10 Goal 的 Review

上一版判断“不要继续堆功能，进入交付闭环”是正确的。

需要优化的点：

1. **部署与证据应前置**  
   上一版建议先写最终文档，再部署和补 Lighthouse。官方模板要求在线地址和演示视频，PDF 要求线上部署和 LCP 指标。因此更稳妥的顺序是先形成交付证据，再填最终文档。

2. **飞书文档形态需要纳入目标**  
   PDF 明确技术文档使用飞书文档撰写；本地 Markdown 适合作为源码留存，但最终提交应准备可分享的飞书文档或至少可复制到飞书模板的内容。

3. **GitHub main/master 是硬交付，不只是本地代码包**  
   提交模板提到代码压缩包，PDF 同时要求 GitHub 完整代码并提交到 `main` 或 `master`。最终 Goal 必须同时覆盖 GitHub 分支和压缩包 / README。

4. **演示视频是独立交付物，不只是脚本**  
   3-5 分钟视频需要能覆盖“创作 -> 审核 -> 分发”全链路。脚本只是中间产物，最终 Goal 应包含录制素材、视频链接或上传位置。

5. **高危识别 90% 的表述要谨慎**  
   当前 33 条 mock eval 和真实模型 smoke test 证明了评估能力与接入能力，但不能直接宣称线上泛化准确率达到 90%。最终文档应写为“样例集内准确率 / 当前基线”，并说明边界。

## 优化后的 Goal Mode 目标

### Goal 0：官方提交差距清单

目标：

```text
对照 PDF 与提交模板，建立最终交付差距清单，明确每个交付物的状态、来源文件、缺口和完成标准。
```

验收标准：

- 新增或完善 `docs/submission-checklist.md`。
- 清单覆盖：在线地址、测试账号、演示视频、项目介绍、技术文档、审核体系、评估报告、代码包、GitHub 分支、自评。
- 每项标注状态：done / pending / not applicable。
- 明确哪些材料来自已有文档，哪些还需新写或部署后回填。

### Goal 1：部署与线上性能证据

目标：

```text
把项目部署到可访问环境，拿到在线体验地址，并补齐榜单页 LCP / Lighthouse 证据。
```

验收标准：

- 有可访问线上 URL 或二维码。
- 测试账号可登录并跑通主链路。
- 生产环境或线上环境记录 Lighthouse / Performance 结果。
- `docs/evaluation-report.md` 更新线上 LCP 数据。
- README 更新部署说明和线上体验说明。

### Goal 2：最终提交文档包

目标：

```text
按照提交模板补齐项目介绍、项目技术文档、审核与质量体系、效果评估、自评，并准备可迁移到飞书模板的最终文档内容。
```

验收标准：

- 新增或完善 `docs/project-introduction.md`。
- 新增或完善 `docs/project-technical-document.md`。
- 新增或完善 `docs/project-self-review.md`。
- 已有 `docs/audit-and-quality-system.md`、`docs/evaluation-report.md` 与最新证据一致。
- 文档显式区分：已实现能力、演示能力、mock 边界、真实模型 smoke test、未来优化。
- 可直接复制到飞书提交模板，或进一步创建飞书提交副本。

### Goal 3：演示视频交付

目标：

```text
完成 3-5 分钟演示视频脚本、录制路径和最终视频交付，覆盖创作、审核、合规改写、分发、详情和技术证据。
```

验收标准：

- 新增 `docs/demo-script.md`。
- 脚本包含时间轴、页面路径、点击动作、解说词、预期画面。
- 演示默认使用 Mock Provider，避免真实模型长耗时影响视频节奏。
- 视频中口播或字幕说明真实模型 smoke test 4/4 通过。
- 产出最终视频文件或可访问视频链接。

### Goal 4：GitHub 与代码交付收口

目标：

```text
完成最终工程清理、敏感信息检查、验证命令、GitHub main/master 分支提交，以及代码压缩包准备。
```

验收标准：

- 不提交 `.env.local`、API Key、数据库文件、构建产物和测试报告。
- `typecheck`、`lint`、`evals`、`build`、`e2e` 全部通过。
- `git status` 无非预期变更。
- GitHub `main` 或 `master` 分支包含完整代码。
- README 包含目录结构、启动说明、测试说明和真实模型 smoke test 说明。
- 代码压缩包可生成，且不含敏感信息和无关缓存。

## 推荐实施顺序

优化后的推荐顺序：

```text
Goal 0：官方提交差距清单
  -> Goal 1：部署与线上性能证据
  -> Goal 2：最终提交文档包
  -> Goal 3：演示视频交付
  -> Goal 4：GitHub 与代码交付收口
```

理由：

- 先做差距清单，避免最后遗漏硬交付物。
- 先部署和测性能，文档中的在线地址与 LCP 数据才不是占位符。
- 再写最终文档，可以直接引用真实证据。
- 演示视频基于最终稳定链路录制，减少返工。
- 最后做 GitHub / 压缩包 / 敏感信息清理，保证提交状态干净。
